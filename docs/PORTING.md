# Porting the Android engine

`engine/src/main/kotlin/org/tgbackup/app/` is a copy of the Android app's engine from
`/root/tg-backup-apk` at commit **`6bdd532`** (v2.2.20, branch `takeout-export`):
`app/src/main/java/org/tgbackup/app/{data,engine,tg,export}/*.kt`, same packages, same file names.
The files were taken with `git archive 6bdd532` (never from the working tree). `ui/*`, `service/*`,
`App.kt` and the Android `SENTRY_DSN` are not copied.

Every file stays byte-identical to the source except the edits listed below.
`tools/engine-sync-check.sh /root/tg-backup-apk 6bdd532` prints `SAME` / `EDITED` / `NEW` / `MISSING`
per file and fails when an `EDITED` file is not listed here.

## Edited files

- `tg/AccountClient.kt`: `android.os.Build` replaced by `DeviceInfo.deviceModel` / `DeviceInfo.systemVersion` (no Android on the JVM).
- `export/ExportManager.kt`:
  - `android.os.Build` replaced by `DeviceInfo.deviceModel` / `DeviceInfo.systemVersion` in the export client's `AppInfo`.
  - `AndroidImageThumbs()` replaced by `JvmImageThumbs()` (Android's Bitmap API is not on the JVM).
  - import of `org.tgbackup.app.platform.DownloadsDir` added.
  - `defaultPath()`: `android.os.Environment` replaced by `File(DownloadsDir.resolve(), "AyuGram Desktop")` (Windows Known Folder, fallback `<home>/Downloads`); same folder name as Android.
- `data/Store.kt`: `writeConfig` and `saveProgress` use `AtomicFiles.replace` instead of `File.renameTo`. On Windows `renameTo` returns `false` when the target exists, so every save after the first was silently lost.
- `engine/LogBus.kt`: rotation to `log.old.txt` uses `Files.move(..., REPLACE_EXISTING)` in its own runCatching, so a failed rotation never stops the append. With `renameTo` the second rotation failed on Windows and `log.txt` grew without limit.

## New files (not in the Android app)

- `export/JvmImageThumbs.kt`: `ImageThumbs` on Java ImageIO (png/jpg only; WebP cannot be written by ImageIO and returns `false`).
- `platform/DownloadsDir.kt`: Downloads folder via `Shell32Util`/`KnownFolders` on Windows, else `<home>/Downloads`.
- `platform/DeviceInfo.kt`: `deviceModel = "TG Backup Desktop"`, `systemVersion = os.name` (e.g. "Windows 11").
- `org.tgbackup.app.BuildConfig` is generated by `engine/build.gradle.kts` into `engine/build/generated/buildconfig`
  (`VERSION_NAME` from `tgbVersion` in the root `gradle.properties`), so the copied `import org.tgbackup.app.BuildConfig` compiles unchanged.

## Not copied

- `export/AndroidImageThumbs.kt`: replaced by `export/JvmImageThumbs.kt`.

## export-core deviations

export-core is shared with the Android app but lives in this repo as its own copy.

- New `org/tgbackup/io/AtomicFiles.kt`: `replace(tmp, target)` = `Files.move(REPLACE_EXISTING, ATOMIC_MOVE)`,
  falling back to `REPLACE_EXISTING` alone when an atomic move is not supported, and retrying up to 5 times
  100 ms apart on `FileSystemException` (antivirus / indexer locks) before rethrowing.
- `mtproto/MtpClient.kt`, `MtpStorage.set`: `tmp.renameTo(file)` replaced by `AtomicFiles.replace(tmp, file)`,
  for the same Windows reason as `Store` (the export session's DC and auth keys were lost after the first save).

## Back to Android

The `AtomicFiles` fix (Store, LogBus, MtpStorage) should also go to the Android repo. It needs care there: `java.nio.file.Files` requires Android API 26, and the app's minSdk is 23.
Port `AtomicFiles` with an API-level guard: `Files.move` with `REPLACE_EXISTING` when `Build.VERSION.SDK_INT >= 26`,
and a `File.renameTo` fallback below that (on Android `renameTo` already replaces an existing file).

## Verified

- Branch `engine-port`: final CI run `41763832454` is green on `linux`, `windows` (runs `gradlew.bat test` for all projects) and `windows-package`.
- Engine smoke on windows-latest:
  - `ENGINE_OK NeedPhone`
  - `NATIVE_TMP_RELAUNCH C:\ProgramData\TGBackup-c368a648\tmp`
  - `ENGINE_CONFIG D:\a\_temp\תיקייה עם רווח\TGBackup\engine-smoke\config_v2.json`
- Local Linux engine smoke prints `ENGINE_OK NeedPhone` and creates `tdlib/smoke/db`.
- Test counts (`./gradlew test`, local):
  - export-core: 37 tests, 0 failures
  - engine: 17 tests, 0 failures
  - desktop: 35 tests, 0 failures
- Finding: `File.renameTo` does not replace an existing file on Windows. Before `AtomicFiles`, every save after the first was silently lost in:
  - `Store` config and progress
  - `LogBus` rotation
  - export-core `MtpStorage` session

  The Windows test job proves the fix.
- Backport: `java.nio.file.Files` needs Android API 26 (app minSdk is 23), so the Android port of `AtomicFiles` needs an API-level guard with a `renameTo` fallback.
- Upstream bug (verbatim `Store.kt`, Android too): `migratedFromLegacy` is declared after `_config = MutableStateFlow(loadConfig())`, so its initializer resets the flag to false after `loadConfig()` sets it. Not fixed here, because the file stays verbatim.
- Task 8 (live read-only check): skipped. It needs the user's login code and will be done with the user.

### Desktop replacements (§5)
- **Foreground service, ongoing notification and `עצור הכל` action:** the Windows tray icon and notification come in plan 5. Until then, sleep is prevented while anything runs and the window shows the state.
- **Storage permission (`אפשר גישה לקבצים`):** dropped. `Export` is always enabled, and the path is typed or the default.
- **Battery optimisation card:** replaced by the desktop `עבודה ברקע` text (the computer does not sleep while a job runs; closing the window does not stop the jobs).
- **`Show my data`:** opens the exported file or folder on the PC (`POST /api/export/open`); an error is a toast.
- **POST_NOTIFICATIONS, intents and FileProvider:** n/a. Links open in the system browser.
